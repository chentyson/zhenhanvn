## 1. 背景与目标

| 目标 | 设计回应 |
|---|---|
| 与 hy2 / vless / shadowsocks 等公开协议均不相似 | 不用 TLS/QUIC 栈；无 ClientHello、无固定首字节；首包 48B 全高熵；UUID 不上线 |
| 每出口节点 ≤100 人 | 服务端对首包按全部用户 key 暴力试解（100 次解密为微秒级），省掉密钥交换与全局密钥 |
| 简化技术、稳定、高性能 | 无证书体系、无 AEAD、无伪装层；拥塞控制/重传全部交给内核 TCP；AES-CTR 硬件加速 |
| 一账号一条连接（服务端强管控） | 服务端按 UUID 维护连接表，新连接 takeover 旧连接；`max-clients` 限节点总连接数 |

## 2. 总体架构

```
客户端(win/mac/linux)                         服务器(centos等)
v2rayN GUI ── xray/sing-box内核 ──┐      ┌── s-ui/sing-box(原有路由出站)
                                  └ socks5 ──> zhdata-tunnel(client)
                                                   │  每节点恰好 1 条 TCP 长连接(zhdata协议)
                                                   ▼
                                        zhdata-tunnel(server, 公开端口)
                                          backend=direct  直接拨目标
                                          backend=socks   转给本机 sing-box socks inbound
```

- 一个二进制、`-mode client|server` 区分角色；协议代码两端 100% 共享。
- 客户端接入 v2rayN：把节点配成 socks 节点，指向 `127.0.0.1:<client监听端口>`，v2rayN/内核零改动。
- 服务端接入 s-ui：sing-box 加一个本机 socks inbound（如 127.0.0.1:12345），tunnel 以 `-backend 127.0.0.1:12345` 对接；测试/直连场景可用 `-backend direct`。

## 3. 协议规范 zhdata-v1

### 3.1 握手（1 个包，48 字节，0 应用层 RTT）

```
偏移0   : salt[16]     明文随机数（本连接唯一）
偏移16  : enc[32]      = Enc_K( "zhv1"(4B) | slot(1B) | conn_rand(7B) | zeros(20B) )
```

- 派生：`PRK = HMAC-SHA256(salt, uuid)`；`key = HKDF-Expand(PRK,"zhdata-v1-key")[0:32]`；`iv = HKDF-Expand(PRK,"zhdata-v1-iv")[0:16]`。
- 服务端对配置里的每个 UUID 重算 key 试解 enc，命中 magic `zhv1` 即确认用户（≤100 用户开销可忽略）。
- `slot`（v0.3）：会话槽位 0–7，客户端 `-conns N` 开 N 条并行会话各占一槽；服务端接管按 (uuid,slot) 隔离，同 uuid 不同槽共存、同槽旧连接收 GOAWAY。slot=0 与旧版语义完全兼容（旧客户端该字节恒为 0）。
- 未命中：按 IP 限频（10 次/分钟）；若前 4 字节像 HTTP 且配置了 `-decoy`，拼接转发诱饵服务，否则直接关闭。

### 3.2 记录层（握手后整条 TCP 流为一段连续 AES-CTR keystream）

```
len(2B大端, = 4+payload长) | type(1B) | stream_id(2B大端) | payload
```

- 读方向、写方向各用一条独立 keystream（同一 key/iv、两个计数器状态），互不干扰。
- 记录开销 4B/≤16KB（≈0.03%）。不做 MAC：TCP 校验和保证传输完整性，垃圾字节只会导致会话关闭（威胁模型：运营商 DPI，非国家级）。

### 3.3 帧类型

| type | 名称 | 含义 |
|---|---|---|
| 0x01 | OPEN | 新建流；payload = `atyp(1B) [len(1B)若域名] addr port(2B)`（与 SOCKS5 地址编码一致） |
| 0x02 | DATA | 数据 |
| 0x03 | CLOSE | 半关闭（发送方结束） |
| 0x04/0x05 | PING/PONG | 30s 心跳；90s 无活动判死 |
| 0x06 | GOAWAY | 服务端宣告被新连接接管 |
| 0x07 | RESET | 流立即中止 |
| 0x08 | OPEN_ACK | 后端拨号成功 |

### 3.4 多路复用与优先级

- 每流一条 pump-up/pump-down 通道；流在会话重连后自动重开（新 sid）。
- 发送队列三级优先：控制帧 > 小 DATA(≤1400B，交互流量) > 大块 DATA（下载流量），避免大流放大丢包停顿对交互的影响。
- 每会话最多 256 流；后端未就绪时 DATA 暂存 ≤512KB 防突发。

### 3.5 会话管控

- 服务端 `map[uuid] -> session`；新连接对旧连接发 GOAWAY + 300ms 后关闭（takeover，换网/重启自动接管）。
- 客户端收到 GOAWAY 后重连；若会话存活 <15s（uuid 争夺失败方），重连退避指数增长（1→2→4→…→60s），避免双方 churn。
- `max-clients`（默认 100）超出时新连接握手前直接关闭。

### 3.6 已知参数（编译期常量）

```
pingInterval=30s  idleTimeout=90s  writeTimeout=15s  handshakeTimeout=10s
backendDialTimeout=10s  maxStreams=256  maxPendingBytes=512KB  maxPayload=16KB
```

## 4. 代码结构（单模块；仅 1 个第三方依赖 modernc.org/sqlite，纯 Go 保持 CGO=0 交叉编译）

| 文件 | 内容 |
|---|---|
| main.go | 命令行、模式分发 |
| config.go | users txt 解析（s-ui 风格 JSON / 字符串数组 / 每行一个 key） |
| keysource.go | **key 多源管理**：`-users` 逗号分隔多路径（txt/sqlite 自动识别），并集去重小写化；20s mtime 热加载；DB 自适应查找带 uuid 列的表；只读打开；全部失败时保底沿用旧列表 |
| crypto.go | HKDF-SHA256、AES-CTR 派生（标准库实现，AES-NI 自动加速） |
| frame.go | 记录编解码、地址编码（**域名带 1B 长度前缀，与 SOCKS5 一致**） |
| session.go | 会话：三优先发送队列 writer、keepalive、读循环 |
| socks.go | 本地 SOCKS5 服务端(client侧) + SOCKS5 客户端(服务端→sing-box)；`ZHD_DEBUG=1` 打开协议级调试 |
| client.go | 本地监听、流管理、重连与 GOAWAY 退避、流重开 |
| server.go | 握手试解、takeover、max-clients、防探测限频、decoy、后端拨号（direct/socks） |
| *_test.go | 单元 + 集成（端到端、错误 uuid、takeover、探测拒绝、socks 对等测试等） |

## 6. 部署

### 6.1 服务端（CentOS 等）

```bash
mkdir -p /opt/zhdata && cd /opt/zhdata
# 上传 dist/zhdata-tunnel-linux-amd64 与 users.txt（每行一个用户 UUID，或 s-ui JSON）
cat >/etc/systemd/system/zhdata.service <<'EOF'
[Unit]
Description=zhdata-tunnel server
After=network.target
[Service]
ExecStart=/opt/zhdata/zhdata-tunnel-linux-amd64 -mode server -listen :443 -users /opt/zhdata/users.txt -backend 127.0.0.1:12345 -max-clients 100
Restart=always
[Install]
WantedBy=multi-user.target
EOF
systemctl daemon-reload && systemctl enable --now zhdata
firewall-cmd --permanent --add-port=443/tcp && firewall-cmd --reload
# 弱网关键：BBR（需内核 >=4.9；CentOS7 自带 3.10 需装 elrepo kernel-ml 或换 Stream9/Rocky）
sysctl -w net.ipv4.tcp_congestion_control=bbr
```

注意：CentOS 7 已 EOL，新部署建议 CentOS Stream 9 / Rocky / Alma。SELinux 默认对 systemd 启动的自定义二进制为 unconfined，绑任意端口可行。

### 6.2b s-ui 集成指南（v0.1，零代码改动）

s-ui/sing-box 不认识 zhdata 协议，也不需要认识：认证与连接管控在 tunnel 层完成，tunnel 以本机 SOCKS 喂给 sing-box。

方式 A（测试最快）：`-backend direct`，sing-box 不参与，无分流/DNS 能力。
方式 B（正式推荐）：
1. s-ui 面板 Inbounds → 添加 socks：listen `127.0.0.1`，port `12345`，无密码（v0.1 socksDial 仅支持无认证），tag 记 `socks-zhdata`；
2. 路由加规则 `inboundTags=[socks-zhdata] -> direct`（默认出站为 direct 时可省略）；
3. tunnel `-backend 127.0.0.1:12345`；
4. 用户 key 来源：直接 `-users /etc/s-ui/private/s-ui.db,/opt/zhdata/users.txt`（v0.2 起 tunnel 原生读 sqlite，20s 内热加载，加删用户无需重启；本机未装 s-ui 时自动忽略该路径）；
5. tunnel 独立端口与原 hy2/reality 入站共存，便于 A/B 对比；`-decoy` 指向本机 HTTP 诱饵。

v0.2 面板向集成：tunnel 暴露 `/stats`（在线 UUID、按用户字节数）→ s-ui 前端 tab 或独立页面读取；不建议现在 fork sing-box 做原生 inbound。

### 6.3 客户端（Windows，配合 v2rayN）

```powershell
zhdata-tunnel-windows-amd64.exe -mode client -listen 127.0.0.1:11080 -server <节点IP>:443 -uuid <你的UUID> -conns 3
# v2rayN 添加 socks 节点: 地址 127.0.0.1 端口 11080
# -conns 3：3 条并行隧道会话（丢包/整形路径下实测把聚合带宽从 1/3 提升到与裸 TCP 持平，见 §7.2）
```

macOS/Linux 客户端命令相同（对应架构二进制）。后续可由 v2rayN CoreManager 机制自动拉起/隐藏（见 §8 路线）。

### 7.0 真实节点部署实测（C498.uwintech.com，CentOS Stream 9，2026-11-13）

- 服务端：systemd `zhdata.service`，`-listen :49888 -backend direct -users /etc/s-ui/private/s-ui.db,/opt/zhdata/users.txt`，BBR 已启用（内核 5.14）。

- 错误 key 客户端：流量不通 ✓；服务端 `-v` 日志可见 `unknown handshake` 拒绝记录。
- **热加载实测**：向 users.txt 追加 key → `hot-reloaded 2 keys` → 新 key 客户端免重启直接 200；删除该 key → `hot-reloaded 1 keys`。两用户并行各一条会话。

开发期间修复的关键缺陷（记录以免回归）：
1. **SOCKS5/OPEN 地址编码缺域名 1B 长度前缀**（读端按 101 字节等待导致全链路卡死）——测试 `TestSocksRawPair` 锁死该行为。

### 7.2 速度问题诊断与 v0.3 修复（2026-11-14，C498 实测）

现象：v2rayN 走 hy2 直连 C498 ≈100Mbps，但 socks→zhdata 隧道 <5Mbps，speedtest.net 卡顿。

分层实测（同机同靶 fsrv:8000，50MB 文件）：

| 路径 | 单流 | 8 并发合计 |
|---|---|---|
| 裸 TCP（python 靶直连） | 35.5–56.9Mbps | ~47Mbps |
| 隧道 v0.2（修复前） | 9–15Mbps | 12–17Mbps |
| 隧道 v0.3（修复后，`-conns 3`） | **42.3Mbps** | **54.0Mbps** |

根因（三个叠加，全部修复）：

1. **CLOSE 帧插队截断下载**（主犯）：`tClose` 走 ctrlQ（最高优先级），大响应时 CLOSE 越过已排队的 loQ DATA 先到对端 → 客户端提前 CloseWrite 本地 socket → curl 见"早 EOF/空响应"、速度计只能拿到碎片。修复：CLOSE 改走 loQ（`sendOrdered`），客户端以 rq 队列 nil 哨兵保证刷完再关；新增 3MB 体响应回归测试（曾稳定复现 3118924≠3145728 截断）。
2. **单连接在丢包路径上的拥塞塌缩**：隧道会话长驻+空闲，BBR 反复进入 PROBE_RTT 且 14.6% 重传把 ssthresh 打到 30，每次突发都要重新爬坡；新建 TCP 的 python 靶没有这个历史包袱。修复：客户端 `-conns N`（1–8）并行会话槽：握手块 hp[4] 携带 slot 字节，服务端按 (uuid,slot) 各自接管互不 GOAWAY；流按最少负载槽分配。N 条独立拥塞窗口 + 独立丢包域 → 聚合带宽线性扩展。
3. 测试方法坑（不是产品问题，但曾误导）：靶机响应行缺 `200 OK` 状态码、curl `-o` 只绑第一个 URL、`pkill -f` 误杀自身 shell、下载中途清理脚本杀了被测客户端。

附带调参：`maxStreams 256→1024`（speedtest 瞬时并发高，RESET 级联雪崩）；发送队列 ctrlQ/hiQ/loQ = 256/1024/1024。cubic 在同路径仅 0.2–2.2Mbps，BBR 保持默认（丢包路径上 cubic 必死，已固化 /etc/sysctl.d/99-zhdata.conf）。

结论：hy2 的 100Mbps 是 QUIC 多流并行 + 新连接拥塞红利的上限；zhdata 修复后在同路径单流/8 并发已**持平裸 TCP（即该路径实际上限）**。要再往上只剩两条路：多槽 `-conns`（已做）或协议级 per-stream 丢包恢复（v1+ 再议，性价比低）。

### 7.3 上传方向 HoL 修复与"TCP vs QUIC 整形"定性（v0.3 补，2026-11-14 下午）

用户复测：hy2 下载100M/上传50M，隧道下载6M/上传仅0.2M。补测上传方向发现：

1. **服务端上传同步写阻塞整条会话（真 bug，已修）**：dispatch 对后端 `bc.Write` 是同步的——任一后端接收慢（speedtest 多流上传必现），单 dispatch 线程被卡死 → 全会话所有流的上传、OPEN/ACK、控制面冻结，下载也随之停（rx 停止读取）。修复：每流独立异步上传队列（upq，64帧≈1MB），dispatch 只入队；队列满只重置该流不动全会话。回归测试 `TestUploadSlowBackendNoHoL`（修复前 fast 请求超时 FAIL，修复后 PASS）。
2. **同窗对照（15:36–15:40）**：裸 TCP 直连 上传3.2/下载5.2 Mbps；隧道（conns=3+全部修复） 上传3.5/下载8.8 Mbps；x4 并行上传聚合≈4Mbps。**隧道已持平裸 TCP，zhdata 在 TCP 层无实现差距**。
3. **剩余差距 = 线路对 TCP 的定向整形（随时段波动）**：同时段 hy2(UDP/QUIC) 可到 100M/50M，任何 TCP（含裸 TCP 对照）被压到 3–8M；多会话聚合也不突破（per-path TCP 总量整形，非 per-flow）。13:50 同一 TCP 路径还能 42–54Mbps，15:40 只剩 3–8M。

**决策点（v1.0）**：要在该线路追平 hy2，唯一路径是承载层换 UDP/QUIC（A2：quic-go，纯 Go 保 CGO=0；zhdata 帧/握手跑在 QUIC 上，天然 per-stream 恢复 + 现成 TLS 外观）。TCP 版在交互/中低带宽场景仍完全够用（§1 目标）。

### 7.4 多端口并行会话——TCP 版追平 hy2（v0.3，2026-11-14 晚，用户思路落地）

用户提问：能否像多线程下载那样，把数据拆成多路并发、服务端汇聚后再转发？实测**证实且已实现**——关键是线路的 TCP 整形按 **(目标IP, 目标端口) 分桶**：

晚高峰（20:15–20:45）对照（50MB 单文件，同窗）：

| 并发方式 | 上传聚合 |
|---|---|
| 单连接（裸/隧道） | 0.6–1.0 MB/s（5–8 Mbps） |
| 4 路·**同端口** | 0.82 MB/s（≈单路，**不涨**） |
| 4 路·**不同端口** | 2.1（裸）/ 2.9（隧道）MB/s（≈3×） |
| **8 路·不同端口（隧道 -conns 8）** | **5.72 MB/s ≈ 45 Mbps（8/8 完成）** |

下载同理：隧道 x8 多端口 **9.3 MB/s（73Mbps+）**，单流 48Mbps。

实现（纯 TCP、不改协议语义）：
- 服务端 `-listen` 支持逗号分隔多端口（zhdata 服务现监听 49888–49895）。
- 客户端 `-server` 逗号分隔多地址，**slot i 拨第 i 个端口**（`servers[i%N]`）；配合 `-conns 8` = 8 条会话各占一个端口桶。
- 每桶仍是普通单条 TLS-like TCP，外观不变；只是从 1 桶变 8 桶。

结论：**该线路 TCP 总量整形不是绝对天花板，按端口分桶**。zhdata 用 8 端口并行会话，晚高峰上传已达 hy2 的 90%（45 vs 50 Mbps）、下载 70–90%（73 vs 100）。QUIC（A2）仍是"最优外观 + 突破分桶"的方向，但**TCP 多端口已足够可用**，非必须。

注意事项/后续：端口桶上限随时段变（白天单桶就能 40+Mbps，晚高峰单桶塌到 <1MB/s）；8 端口是"更多连接数 vs 隐蔽性"的权衡，交互用户可降 `-conns 2`；桶是否也按源IP聚合、跨不同远端节点是否更优，留待多节点验证。

### 7.5 上传 0.2–0.5Mbps 真凶：帧乱序 + 误杀背压（v0.3 关键修复，2026-11-14 深夜）

用户 speedtest 上传长期 0.2–0.5M，而我的 curl 对照始终正常——差异在**sing-box 写 socks 的块尺寸不规则（TLS 记录级，数百~1400B）**，暴露两个协议级 bug：

1. **DATA 帧乱序（致命）**：`sendData` 把 ≤1400B 的小帧塞进高优先队列 hiQ，16KB 大帧走 loQ——**同一条流**的混合尺寸帧在慢链路上互相超车（流没有序号，任何越序=数据损坏）。curl 全是均匀 16KB 读，永不触发；speedtest/sing-box 必触发 → 流损坏 → 应用重试 → 0.2–0.5M。确定性测试 `TestSessionDataFIFO`（net.Pipe 积压三帧，修复前乱序 FAIL）。修复：**DATA 一律走单条 FIFO 队列**；交互隔离靠 `-conns` 多槽（least-loaded 选路），不靠帧级插队。
2. **队列满即杀流（误伤）**：upq 64 帧满 → RESET 流。POST 灌体（speedtest 行为）天然突发，健康流也会被误杀（本地 5 并发上传测试全部中断复现）。修复：**背压而非丢弃**——dispatch 阻塞等待（TCP 窗口逐级回传压力到应用），仅 3s（upq）/10s（拨号）真停滞才只重置该流。pending 上限 512KB→2MB，upq 64→128 帧。新测试 `TestParallelBulkUpload`：5 并发 ×20MB POST，全部 sha256 逐字节验证通过。

**修复后 WAN 同窗对照（22:2x 晚高峰）**：

| | 上传聚合 | 下载单流 |
|---|---|---|
| 裸 TCP ×4 | 815 KB/s（200×4） | 615 KB/s |
| 隧道 ×4（8 槽多端口） | **1,224 KB/s（200×4，反超裸 TCP）** | **1.14 MB/s（反超）** |

所有流全程存活（fsrv 收到的字节与 curl 发出精确吻合），此前"000"均为 `-m` 超时假象。**结论：上传路径已修复且优于裸 TCP；hy2 的 50M 上传仍是 UDP 特权（见 §7.3/7.4）。**

附：本轮排障踩坑记录——C498 系统时区是 UTC（journalctl 用 `-15min` 而非本地钟点）；部署脚本必须显式 `GOOS=linux`（曾把 Windows exe 部署到 systemd，Exec format error 崩溃循环）；python 靶机排空仅 ~1MB/s，压测靶机用 Go 版（tools/fsrv，支持端口参数与 POST 排空）。

### 7.6 16 槽并行 + TCP 缓冲拉满（v0.3，2026-11-14 深夜）

用户复测双向 ~30Mbps 后追问"TCP 为何只有 QUIC 的 30%"。定量解释：10% 丢包 + 170ms RTT 下，单条 TCP/QUIC 抗损能力其实接近（都要重传）；hy2 的优势 = 线路对 UDP 的**分类豁免**（主因）+ per-stream 恢复 + 更激进拥塞控制。对策是把 TCP 侧的"桶数"和窗口拉满：

- `maxSlots` 8→**16**（服务端监听 49888–49903 共 16 端口=16 个整形桶，slot i 拨端口 i）
- 会话两端显式 `SetReadBuffer/SetWriteBuffer = 16MB`（170ms×100Mbps BDP≈2MB，自动调优不够）；C498 `net.core.rmem_max/wmem_max=32MB`

深夜（23:0x–23:1x，线路回稳）16×10MB 聚合实测：

| | 隧道 x16 | 裸 TCP x16 | hy2 |
|---|---|---|---|
| 下载 | **13.5 MB/s (108M)** | 19.1 MB/s (153M) | ~100M |
| 上传 | 3.4 MB/s (27M) | 7.0 MB/s (56M) | ~50M |

下载已追平 hy2。隧道 vs 裸 TCP 仍有 30–50% 差距（16 流下隧道多一跳 + 双端加解密/拷贝 + 服务端 VM 资源），这是隧道自身的税，v1.0 可通过 zero-copy/向量写收窄。同时修正一条旧结论：整形并非严格按端口（裸 x16 打 8 个端口仍到 19MB/s）——更接近按流/按桶混合，**多会话并行始终是正确杠杆**。

### 7.7 v0.4 流内并行实验（zhv2 协议地基，2026-11-15 上午）

用户复测：下载 93–96M（追平 hy2），上传 4.5M。取证（客户端 pumpUp 计数 + 服务端 journal）：speedtest 一轮开 ~958 条流，**真正传数据的只有 4 条**（各 25MB）；服务端零 stall/reset——4.5M = 4 桶 × 单桶 ~1.1MB/s 上限，**是并发数问题不是 bug**。同窗对照：隧道 x16 上传 8.4MB/s 追平裸 TCP。

实现用户设想的"流内拆包并行"（协议升 **zhv2**：sid 每 uuid 全局唯一、上行 DATA 帧带 4B 序号、tClose 带 finSeq、服务端 (uuid,sid) 全局重组 + upq 重放；快槽超过重组窗口时 **park 等待慢槽**（TCP 窗口回压=按流真流控），`rxWake` 广播唤醒（容量=maxSlots，单 token 会惊群死锁）；客户端 `-spread` 控制单流最大铺槽数，槽选择按 loQ 积压最小）。

**实测结论（关键教训）**：
- `spread=2` 单流上传 **6.16MB/s ≈ 49Mbps = 裸单流的 2.2×** —— 用户设想被证实；
- 但**帧级轮询铺 M 槽，输出 = M × 最慢槽速率**；M≥4 或多流各自再铺多槽时，桶速差导致 park/唤醒抖振，反而跌到 0.9–2.4MB/s；
- 因此 **默认 `-spread 1`（关闭）**，保持 v0.3 已验证行为；zhv2 序号/重组地基保留。

**v0.5 正确姿势（待做）**：仿多线程下载——**段级并行 + 段完成 ACK**（新帧型 tSegAck），客户端按"槽完成一段再领下一段"的拉式分配，段大小动态（快槽大段慢槽小段），输出 ≈ Σ 各槽速率而非 M×min。预期把 v2rayN 这类"只开 4 条流"的应用上传再翻倍。

定版回归（10:0x，spread 关）：单流上 5.4MB/s、单流下 7.0MB/s、x16 下 14.6MB/s（117M）、x16 上 7.6MB/s（61M），无失败流。

### 7.8 v0.5 段级思想落地：按槽 credit 拉式并行（zhv3，2026-11-15 上午）

v0.4 失败的根因是**帧级轮询强制每槽均摊**（输出 = M × 最慢槽）。v0.5 保留帧粒度但改为 **拉式分工**：服务端每槽每收 16 帧回一条 `tAck(sid, N)`（sendCtrl 走 ctrlQ，不被下行拥塞挡住）；客户端按"该槽未确认帧数 < 该槽自适应窗口（AIMD：排空快→×2，积压 3/4→×0.75，范围 4–96 帧）"挑槽投放——**慢槽自然少领、快槽多领，输出 ≈ Σ 各槽速率**。`-spread` 默认 4：一条 bulk 流铺到 4 槽各占一个整形桶。

配套修复：spread 槽中途死亡 → 其在飞帧永久丢失，detach 时**立即截断重组空洞**（rx.next 跳过缺失序号，高序号缓冲帧继续流动，损失语义与 v0.3 in-flight 丢失一致）；fin 判定全部改 `rx.next >= finSeq`。

实测（同窗对照，白天深整形窗）：

| 场景 | 上传 |
|---|---|
| RAW 单流 | 0.48–0.68 MB/s |
| **v0.5 单流（spread=4）** | **1.23–5.28 MB/s（2.5–3.1×）** |
| **v0.5 x4（v2rayN 等效场景）** | **agg 6.4 MB/s = 51M，4/4 完成**（≈ 16 桶总池 56M 上限） |
| v0.5 x4 下载 | agg 10.0 MB/s，4/4 |

结论：v2rayN 这类"只开少数上传流"的应用，上传上限从 **N 桶** 提升到 **N×spread 桶**（封顶 16 槽总池），4.5M/8.3M 时代的结构性瓶颈解除。zhv3：tAck(0x09) + magic 升档，新旧版本不能互通（部署需双端同步）。

### 7.8.1 槽数扩容 16 → 32（同日中午）

用户实测 speedtest 上传 30M（= 16 桶 × 当时单桶 ~1.9MB/s），未及 hy2 的 50M。同窗探底：裸 TCP x16=8.3、**x32=10.8、x64=13.4MB/s（107M）**——线路是**按流配额制**且流数收益近似线性（未见硬顶），于是 maxSlots 16→32（zhdata systemd 监听扩到 49888–49919，drop-in `ports32.conf`；spread 默认 4→8，4 应用流 × 8 槽 = 32 桶刚好铺满）。

复测（32 槽，隧道）：单流上 2.0MB/s、**x4 上 agg 6.1MB/s = 49M，4/4（≈ hy2 50M）**、x4 下 96M。64 流仍在线性区，v1.0 若继续扩槽需先解决隧道自身 CPU 税（x32 隧道 6.1 vs 裸 32 流 10.8MB/s）。

### 7.8.2 日志降噪 + credit 调参（同日中午）

- speedtest 的 ~958 条探测流正常结束会刷屏 `pumpUp EOF`；探测被 app 强拆（RST/teardown 竞态）刷 `use of closed network connection`/`forcibly closed`。均为正常 churn，`streamChurn()` 白名单（EOF/ErrClosed/ECONNRESET+文案匹配）静默，只留真异常。
- spread 前缀税定位：慢槽初始 credit 32 帧（512KB）拖尾 ~5s，快槽 park 空等。调参 `laneCapInit 32→8`、`ackEvery 16→8`（AIMD 快 4 倍收敛）。同窗对照：池子(RAW x32) 8.6MB/s 时隧道 x4 从 4.85 → 5.4–6.0MB/s（**对池比 53%→63–70%**）。剩余 ~30% 为 TCP 前缀保序固有代价（QUIC 无此税），v1.0 方向：按槽乱序 write-through 或更大乱序窗。

初判为"测量口径"（ramp+探测），但用户第二轮只有 7M 暴露了真问题——见 §7.8.3。

### 7.8.3 多流死锁（第二轮 7M）+ 自动铺槽预算（同日中午）

- **现象**：speedtest 第一轮 ~30M、第二轮仅 7M；服务端 journal 显示第二轮是 **19 条大流并发、共 418MB 完整收满**，协议层零异常（无 gap/overflow/reset）。不是线路波动，是 bug。
- **复现**：本地 `TestParallelBulkUpload`（5 流 × 3 槽）3/3 必卡，每条流停在 ~8MB。goroutine 栈：客户端 `pumpUp` 卡在 `sleepSelect`（等 credit），服务端 `pumpUp` 全空闲 → 数据不再流动。
- **状态快照定位**（临时 diag dump）：卡死流客户端 `sent=861 ack=856 cap=4`（outstanding=5 > cap=4，**credit 为负**）；服务端该 lane `count-acked=5 < ackEvery=8`（未攒够不发 tAck）。**客户端等 ack 才发、服务端等帧才 ack → 死锁。**
- **根因**：AIMD 把 cap 收缩到 `laneCapMin=4`，**低于 `ackEvery=8`**。单 lane 流一旦 cap<ackEvery：客户端发满 cap(<8) 停发，服务端只收到 cap(<8) 永不凑满 ack 阈值 → 互等死。之前 3-lane spread 时被"别的 lane 还能发"掩盖；自动铺槽预算让单流独占 1 lane 后暴露。
- **修复①（不变式）**：`laneCapMin ≥ ackEvery`（二者=8）。使"信用耗尽(out==cap)"必然蕴含"服务端已收到 ≥8 帧、已发过 ack"，循环等待不可能成立。
- **修复②（自动铺槽预算）**：每流 lane 数 = `conns ÷ 活跃大流数`（`clientApp.bulk` 计数：流发送超 spreadThreshold=128KB 记一次，teardown 递减）。少流→铺满（4 流→8 槽）；多流→自动退回 1–2 槽/流独占（19 流→1 槽），杜绝 19×8=152 槽需求挤 32 会话把每槽份额切碎。
- **验证**：`TestParallelBulkUpload` 3/3 必挂 → **5/5 通过**；真实链路 16 并发流上传 **58M 不死锁**（修复前该形态=7M）；单流 spread x4 = **46.9M**（对池 9.2MB/s 的 64%，≈ hy2 50M）。

### 7.8.4 64 槽试验与天花板画像（同日下午）

`maxSlots 32→64`（slot 握手字节 <256 安全；rxWake/预算自适应）；systemd drop-in 换 `ports64.conf`（49888–49951，64 监听验证 ✓）；bat 改 `-conns 64`、`-spread` 默认 8→16。全套回归绿、64/64 建立、无死锁。

同窗形状扫描（10MB/流，KB/s 聚合，13:0x 时段，池子 RAW x64 = 15.9MB/s = 127M）：

| 隧道形状 | 每流槽数(自动预算) | 聚合 | 对池 |
|---|---|---|---|
| x4 流 | 16 | 5.55 MB/s = 44M | 35% |
| x8 流 | 8 | 5.91 MB/s = 47M | 37% |
| x16 流 | 4 | 7.83 MB/s = 63M | 49% |
| x32 流 | 2 | 8.88 MB/s = 71M | 56% |
| **x64 流(独占)** | 1 | **10.9 MB/s = 87M** | **68%** |

结论画像：
1. **线路池仍随流数近线性增长**（x16≈8.3、x32≈9–10.8、x64≈13–16MB/s），暂未见硬顶。
2. **隧道吞吐主要不是 CPU**（两轮扫描客户端 CPU 仅 ~3s），而是**前缀保序代价随每流槽数超线性恶化**（M 槽流的输出受最慢 lane 拖尾，AIMD credit 只能缓解）。单流多槽是低效区；多流各占少槽逼近裸 TCP。
3. 即使 1:1 独占形状，隧道仍有 ~32% 恒定税（帧化/搬运/双端 pump 链）——v1.0 零拷贝的目标就是把这截吃掉。
4. 实用含义：v2rayN 类 app 并发流越多，64 槽收益越大；4 流场景 64 槽 vs 32 槽无差别（spread 封顶），不必强推 64。

### 7.8.5 64 槽回归：铺槽超订与全局槽预算（同日下午）

用户 speedtest（64 槽/spread16）：下 70–80M（原 96）、上 18–30M。客户端日志定位：**speedtest 时段 34 条流各自铺到 16 槽**——首波 4–6 条流趁 bulk 计数小把 ladder(128KB/槽) 迅速拉满 16，后续十几条流到达时旧流**不释放**，总铺槽需求 ~100+ > 64 会话 → 每 session 串行 dispatch 2–4 流、16 槽前缀等待互相放大；下载同理（每 session 下行走串行队列，被铺槽流挤慢）。

修复：**全局铺槽硬预算** `app.lanes ≤ cfg.conns`（teardown 释放 attached；与 per-stream 预算 conns/bulk 叠加）。19 流洪水复测：隧道 **67M vs 裸 75M（89% 对池）**——修复前同形状 18–30M。spread 事件日志确认 ladder 被预算自然截断（各流停在 6–8 槽）。

教训：**任何“每流独立”的资源策略必须叠加全局预算**；ladder 阈值(128KB)意味着中等流(2MB)也会铺满，先至者占坑、后至者饿死是并发系统通病。

**64 槽生产回滚（同日 13:3x）**：用户再测两轮 70M/3.2M。客户端日志实锤：**speedtest 突发启动瞬间 64 条隧道连接中 24 条 wsarecv 超时死亡**（服务端 24 ended + 24 re-established，无 max-clients 拒绝）——home 会话死亡连带杀死其上的流 → speedtest 重试风暴 → 3.2M 坍塌形态。结论：**64 常驻 TCP 超过家宽路由/ISP 在突发时的并发流承载**（全天 32 槽零断连）。协议保留 maxSlots=64 能力，**生产参数回滚 -conns 32**（自动预算+全局槽预算保留，对 4-19 流形态最优分配 32 已足够）。回滚后快速验证：TUN x4 = 53M。家宽侧流数天花板：观测介于 32(稳) 与 64( bursts 死 24/64) 之间。

### 7.8.6 credit 时钟限流：6M 隐形天花板（v0.6，同日下午）

用户 32 槽回滚后 speedtest 上传仍 ~5.6M，形态"2M×5s → 跳 10M → 回落 5M"。**签名分析**：回落值 5M ≈ 单 lane credit 下限 8 帧 × 16KB ÷ 170ms RTT = 0.75MB/s = 6M——**credit 本身成了速率限制器**而不是线路。机理：WAN 稳态下发送端持续把 credit 填满(out≈cap)是**正常现象**（线路排空慢于 credit 时钟），但 AIMD 收缩条件 `out*4>=cap*3` 将其误判为拥塞一路缩到下限；增长条件 `out*2<=cap` 在 out≈cap 时永不触发。少流场景(每流 1-2 有效 lane)整体被钉在 ~6M；"跳 10M"= spread ladder 接通瞬间。

**v0.6 修复**：credit 是纯流控，拥塞控制归底层 TCP——**静态大 credit** `laneCapInit=laneCapMin=laneCapMax=96`（AIMD 退化为常量；不变式 ≥ackEvery 保持；单 lane 时钟上限 9MB/s ≫ 任何整形桶，线路决定速率；乱序拖累由 8MB park 兜底）。实测：**单流上传 6M → 21.6M/17.2M**（spread 生效），x4=36.6M（该时段池波动）。全套回归绿 + 死锁场景 3/3。

### 7.8.7 v0.7：乱序压力反馈 credit（同日下午）

v0.6 静态 96 帧在真实链路反噬：每流 16 lane×96 帧≈24MB 在途 ≫ 8MB 乱序窗 → **全员 park 失速(0.2M) → 15s watchdog 重置 → 新流 5M** 的锯齿（用户实测"跳5M→落0.2M→又5M"）。两端都错的本质：**credit 的正确大小 = 使该流乱序积压不触 park 的最大值**，而这只有服务端知道。

**v0.7 设计**：tAck payload 扩为 8B=`count|bufN`（服务端每流乱序缓冲字节数，st.mu 内捕获；旧客户端读前 4B 兼容）。客户端 applyAck 改为**乱序压力 AIMD**：`bufN < maxReorderBytes/2(4MB)` → +16/ack（浅乱序=该 lane 跟得上最慢 lane，扩窗口）；`bufN ≥ 4MB` → ×3/4（深乱序=有 lane 拖后，缩窗防 park）。`laneCapInit=16, min=8, max=96`（min≥ackEvery 不变式保持）。实测：单流 18.2–21.3M、x4=35M，锯齿消失；全套回归绿、死锁 3/3。协议版本 tAck 8B——**双端需同步部署**（4B 兼容旧客户端）。

**v0.7.1 温和化（同日 13:5x）**：用户报告上传"跳→坠→缓升"锯齿而下载平滑——下载是单热会话纯 TCP 爬坡；上传每条新流重演自适应瞬态：起步 16 帧瞬冲(跳) → 铺开多槽后 bufN 冲过 4MB，×3/4 把**所有** lane(包括无辜快 lane)砸到地板(坠) → +16/ack 与 128KB/槽爬回(缓升)。调参：`init 16→32`（起步时钟 3MB/s 高于任何整形桶）、缩 `×3/4→×7/8`、恢复 `+16→+32`。同窗池比保持 ~76%（该小时裸池仅 49M，绝对值随线路小时窗浮动）。

### 7.9 v0.10：晚高峰"5M→1M→末段15M"根因与修复（2026-11-15 晚，真实 speedtest 复现）

用户复测（19:00-19:20，speedtest.net 经 v2rayN）：上传先冲到 ~5M、随后跌到 1M 徘徊、最后 5s 才到 15M；下载 30-60M；hy2 同线 50M/100M。v0.9.1 的 zbench 画像（fsrv 靶）却始终 p50 50M+，说明难点只在**真实应用形态 + 坏小时窗**。

**取证（本次会话）**：
- 用户 19:05 轮：3 条上传流各 spread 16 lane，服务端 `reorder park bufN=16.79MB next=19/32/37` + `backend stalled` + closeStream RESET（16 members）+ 客户端 tReset 风暴；19:10 轮无 park，但 4 流 24s 只写 26MB。
- 用 headless Chromium 经本隧道跑**真实 speedtest.net**（`tools/speedtest_cdp.js`，playwright-core + 本机 chromium）稳定复现：上传阶段 4 条流 → `reorder park sid=7896 bufN=16,779,346 next=106` → `backend stalled` → 浏览器测速卡死 125s；修复前一次 web 测速上传仅 37.6MB/22s（≈13.7M）。
- 客户端信用诊断（新增 `ZHD_DEBUG2=1` 打印每 lane cap/out、帧/字节）：旧 out-AIMD 的 cap 长期停在 18-36（远达不到 96），且 out≈cap；`-spread 1` 时单 lane 仅 ~2.4Mbps、4 流 ~12M。**这是"必须铺 16 槽才能到 50M"的真正原因。**

**根因（两条叠加，均为结构性）**：
1. **帧数制 out-AIMD 自限（单 lane 时钟）**：每收一个 tAck 客户端立即把窗口填回 cap，`out*2<=cap` 的增长分支几乎不触发、`out*4>=3cap` 偶尔收缩 → cap 不动点 ≈24 帧（384KB）；200ms RTT 下单 lane ≈2.5Mbps。想上 50M 只能叠 16 lane。
2. **逐流铺槽 + 到达制 tAck + park 阻塞 session reader**：16 lane 中任一 lane 停摆 → 小序号洞；tAck 按"到达"计费（帧进了 rx.buf 就算数，不看是否已按序投递），其余 lane 继续把 16MB 乱序缓存灌满；越窗时 park 写在 `session.run` 的读循环里（该 session 上所有流 HOL），而洞帧若排在某个已 park 的 reader 后面就自锁 → 只能等 gapWaitTO=15s / backend stalled 才 RESET。用户看到的"1M 徘徊、末段 15M（解冻后一次性 flush）"即此。

**修复（v0.10；无线上帧格式变更，但双端需同步升级）**：
1. **静态大信用窗口** `laneCapInit=Min=Max=96`（1.5MB/lane）：单 lane 恢复 TCP 线速（不再有 AIMD 极限环）。
2. **默认关闭逐流铺槽** `-spread 1`（main.go 默认 + bat）：一条应用流 = 一条 session，服务端不存在乱序重排，park 在结构上消失；浏览器/speedtest 这类多连接应用自带并行度（4-9 条），逐流铺槽反而制造重排风险。
3. **服务端删除 reader park**：乱序越窗只 RESET 该流（新日志 `reorder overflow ... -> reset stream (reader unblocked)`），session 上其它流继续；代价是该流失败由应用重试，不再整池冻结 15s。
4. **客户端重连窗口不再丢 chunk**：无 live lane 时重试同一 seq（服务端按 seq 去重），避免静默截断导致的应用层数据损坏。
5. 回归测试改写（`stress_repro_test.go`）：从"证明会 park"改为"越窗只重置该流、不阻塞同 session 其它流"+"静态窗口不变式"。

**实测（20:0x，同窗对照，fsrv 8 靶全活）**：

| 场景 | p50 | p10 | 备注 |
|---|---|---|---|
| 裸 TCP x4（线路本底） | 29.9M | 10.5M | 20:09 窗 |
| 隧道 x4（spread=1 + 静态窗） | **56.6M** | 37.7M | 同窗，已 ≥ 裸池 |
| 真实 speedtest（修复后，浏览器） | 下载 73.05M / 上传 18.7M | — | 上传阶段 **0 次** park/stall（修复前同场景必 park）；上传读数受分钟级线路波动影响大 |
| spd 4 流打真实 Ookla 上传端点（隧道） | ~40M | — | 与"裸 TCP 直连同一目标 ~40M"持平 |

**结论**：修复后上传不再出现 1M 徘徊/塌方，单流回到 TCP 线速、多连接应用按各自 flow 数聚合（当晚 4 流 ~40M 量级）；剩余与 hy2 的差距是 **TCP 被按 flow 整形 + 应用只开 4-6 条连接**，要追平 50M/100M 只有两条路：带重传的多 lane 单流（协议行为增强）或 UDP/QUIC（重大架构，见 §10.6）。

**v0.10.1 追加（同晚，下载侧健壮性）**：把压测延长到 4×50MB 隧道下载时发现一次**卡死**——某 session 被服务端 writer 的 15s 写超时关闭，客户端重连后把该流"重开"（对新 session 重新 OPEN → 服务端重新拨后端），把一份全新的 50MB 响应拼进已消费一半的本地 socket → curl 永久挂起。三处修复：① 客户端下行 dispatch 在 rq（64 帧）满时**最多等 2s**，超时只失败该流（不再无限阻塞 session reader → 避免整个 session 被写超时连锁杀死）；② session 死亡时，**homed 在该 slot 的流立即 teardown（fail-fast）**，让应用重试，不再"重开续传"造成数据损坏/挂起（spread lane 流保持存活语义）；③ 服务端 writer 写错误带耗时/帧类型/sid 日志（以前是静默 close，无法定位）。验证：同一 4×50MB 隧道下载测试 **74.1s 全部完成、0 次 session ended/write err**（修复前该场景 session 死亡 + curl 挂死）。同窗单流隧道下载实测可达 61Mbps（线路当时允许），4 流聚合 21.6M vs 同窗裸 TCP 46.5M——**下载聚合同样受 flow 数量与 TCP 整形约束**，与上传结论一致。

**v0.10.2 追加（同晚，home slot 轮转）**：发现 `pickConnLocked` 在 slot 全空闲时并列，永远选 `conns[0]`，于是浏览器 4-6 条流全部落在 **0-3 号 slot**（旧构建客户端日志实测：17 次 `open ack` 全在 slot 0/1/2/3），其余 ~28 条会话全程闲置——这几条被反复复用的长寿命 TCP 流会累积丢包/乱序历史（Windows 侧 CUBIC 无法调优，cwnd/ssthresh 被历史拖低），而裸 TCP 对照每次都是新建流、没有历史包袱。修复：home slot 选择加**轮转游标**（members 数并列时轮转分配，新流依次落到不同 slot）。单流交替对照（3 组，20s/组，同窗）实测隧道单流 p50 = 6.3/8.4/12.6M vs 裸 TCP 单流 p50 = 12.6/10.0/3.1M → **单 flow 速率已与裸 TCP 持平**，隧道自身不再是单流瓶颈；晚高峰聚合差距来自「应用连接数 × 线路 per-flow 容量」。

### 7.10 v0.11（路线 A）：未 ack 帧重传 + 按投递流控 + 重新启用逐流铺槽

用户批准路线 A 后实现。**协议语义变更（magic `zhv3`→`zhv4`），双端必须同步升级**；帧格式本身不变。

设计（client.go / server.go / session.go）：
1. **投递制流控**：服务端 tAck 载荷第二字改为 `deliveredPrefix = rx.next-1`（已按序交给后端的帧数；旧版这里是 bufN 反馈，客户端原本忽略，所以旧客户端不受影响，但新客户端不能被旧服务端服务 → 用 magic 升档强制双端同步）。客户端每流滑动窗口 `streamWindowBytes=4MB`、全局 `globalWindowBytes=64MB`，只有"已投递"才释放帧与窗口 → 服务端乱序缓存天然 ≤4MB（远低于 16MB 上限），后端慢时窗口自动停发（真正的端到端背压，替代旧 per-lane 帧数 credit）。
2. **重传缓冲**：客户端每流保留未投递帧（seq+payload）；全局 200ms stall sweep 检测——某 lane 的到达计数 1.5s 不前进，或其 session 死亡 → 该 lane 的在飞帧换其它 live lane 重发；服务端按 seq 去重。重传不重复记账（同一帧只计一次、只在投递后释放）。
3. **服务端配套**：session 死亡不再立即 truncate 洞（等客户端重传；旧实现会在重传到达前跳洞造成数据损坏）；新增 **hole watchdog**（洞 5s 未被重传填上 → 只 reset 该流）；tClose 时补发一次 tAck（稀疏尾部/单帧请求也能让客户端立刻释放窗口并收尾）。
4. **重新启用逐流铺槽**：`-spread` 默认 8（保留自动预算 `min(spread, conns/活跃大流数)` 与全局 lane 上限，浏览器 4 条流 → 32 lane）。

验证（本地确定性）：
- 白盒 `TestStressUploadWindowAndRetransmit`：窗口只按投递释放（lane 到达计数不释放）；停摆 lane 的帧全部迁到其它 lane；窗口记账全程不漂移。
- 端到端 `TestRetransmitSurvivesSessionKill`：8MB 上传铺 2 lane，中途 kill 一条 lane 的 TCP（在飞帧丢失）→ 目标收到**完整 sha256**（无重传时该测试必然失败）。
- 全套回归 `go test` 全绿。

WAN 实测见 §7.11（部署后）。

### 7.11 v0.11 实测验证与“单流多 lane 吞吐律”（2026-11-15 晚）

**决定性对照（本地回环）**：本机起 `zhdata server -backend direct` + `client -conns 32 -spread 8`，headless 浏览器跑真实 speedtest：**上传 45.02M、下载 83.64M**（RTT≈0）。→ 浏览器供数能力、多 lane 实现、协议机制本身不是瓶颈。

**关键吞吐律（轮询分配的陷阱）**：一条应用流在 N 条独立 TCP lane 上按轮询分帧时，序列交付要求每第 N 帧到达；因此**流吞吐 ≈ N × 最慢 lane 速率**（不是 N × 平均）。实测 WAN 8 lane 单流只有 ~3Mbps（各 lane 0.3–1.5M，且常有一条停摆），浏览器 4 条上传流合计 8–12M——与“1M 徘徊”时期的量级一致，只是现在不再塌方。

**v0.11.1 修复：ETA 车道分配**。每次发送选 `ETA=(pendingFrames+1)/laneRate` 最小的 lane；`laneRate` = tAck 到达计数的 EWMA；**400ms 无进展的 lane 视为最慢**（否则未测速/停摆 lane 会保留初始权重，把帧吸进洞里）。慢 lane 按比例少分帧后，单流吞吐趋近 Σ lane 速率而非 N×min。

**A/B（同一分钟并发，两个客户端各 2 应用流）**：

| 轮次 | spread=8 p50 | spread=1 p50 | 说明 |
|---|---|---|---|
| 1 | **12.6M** | 4.2M | 线路有余量，铺槽 3× |
| 2 | 20.4M | 21.0M | 线路本小时已封顶，二者相同 |

**稳定性**：稳定窗口内 `hole unfilled / reorder overflow / backend stalled` 均为 0；仅在一次线路骤降窗口出现 hole 重置（已将 `holeTimeout` 12s + fast-hole 重传 400ms）。`go test` 全绿，含端到端 `TestRetransmitSurvivesSessionKill`（kill 一条 lane 后 8MB 上传 sha256 完整）。

**结论**：
- 路线 A 已完成并双端部署：单应用流可安全铺多 lane；有线路余量时单流/聚合吞吐可数倍提升；无余量的时段它不会伤害吞吐（spread=1 相当）。
- 浏览器 speedtest 在**晚间 TCP 被重整形时段**上传仍只有 8–18M：该时段线路 TCP per-flow 仅 2–3M、总池 20–40M（同窗裸 TCP x4 25–50M 剧烈振荡），隧道已贴池。hy2 的 50M/100M 是 UDP 路径不受 TCP per-flow 整形，而非协议实现差异。
- 因此“追平 hy2”仍指向路线 B（QUIC/UDP）；路线 A 是 TCP 版能做到的正确形态。下行目前仍单 lane/流，如要下载也聚合需做下行拆分+重组镜像（未做）。

### 7.12 v0.11.2 / v0.11.3：回归修复与“浏览器上传归因”

**v0.11.2（服务端，严重回归）**：`holeSince` 在**后端拨号前**缓冲的帧上也被置位（此时不是洞，openBackend 会按序 flush），且 flush 时不清零 → 每一条多帧请求（尤其是下载请求）会在 **12s 后被 hole watchdog 误杀**。表现：单流隧道下载从 55M 掉到 0.2–1.4MB/s 且游标卡死，浏览器下载 2.7M。修复：仅当 `backend != nil` 时计洞、openBackend flush 后清零、watchdog 要求 `bufN>0`。修复后**单流隧道下载 6.9MB/s=55Mbps**（此前 0.2–1.4MB/s），真实浏览器 speedtest 下载 **86.5–95.1Mbps**。

**v0.11.3（客户端，两个会冻结全局的阻塞点）**：① `tClose` 的 rq 投递是**无界阻塞**的，app 读端一旦退出/滞后就会把 session reader 永久卡住 → 服务端 15s 写超时杀 session → 流失败（下载卡死的另一半原因）；改为与 DATA 相同的 2s 有界等待。② `sendCtrl` 在 ctrlQ 满时阻塞，而 `openStreamLocked` 是在 **app.mu 内**调用它 → writer 卡一次就能把全部 dispatch/ack 拖死；改为非阻塞+队列堵塞即关闭该 session（writer 已卡的 session 本就该放弃）。③ `sendFin` 改为在 app.mu 外、带 2s 上限发送。④ 增加 `dispatch slow`/`pumpDown slow` 诊断日志。

**ETA 计分修正（v0.11.3）**：ETA 的 pending 必须用**真实在 TCP 队列里的帧数** `laneSent-laneAck`，不能用"未释放窗口字节"——后者在跨 lane 的洞存在时会把所有健康 lane 的 pending 一起抬高，反而让分配偏向真正慢的 lane。已加入 `laneSent` 计数并按 backlog 计分。

**浏览器上传归因（关键证据）**：在浏览器 speedtest 上传阶段抓客户端 dbg 状态，窗口是**空的**（例：`sent=4.15MB frames=284 inflight=16KB acked=283`）——隧道根本没有限制，是**应用只喂了 ~2.1Mbps/流**。同分钟隧道 `zbench x4+探测 p50 40.0M`（同窗裸 TCP x4 22.5M / x8 43.0M，隧道 ≥ 裸池 4-flow），同一浏览器走**本地回环隧道**可喂 45M。→ 浏览器 4 条连接在 200ms RTT 下只喂 4–13M，瓶颈在**浏览器↔Ookla 的应用层流控（HTTP/2 窗口等）与高 RTT 的组合**，不在隧道内部（隧道传输的是内层 TLS 字节，无法改变该流控）。hy2 的上传更快可能来自 UDP 下行无 HOL/窗口更新更及时（或测试服务器/时段不同，待同分钟 A/B 验证）。

**同窗总表（22:05-22:07）**：

| 场景 | 结果 |
|---|---|
| 隧道 x4+探测（spread=8+ETA） | p50 **40.0M**（p10 19.6） |
| 裸 TCP x4 / x8 同窗 | p50 22.5M / 43.0M |
| 浏览器 speedtest 下载 | **86.5–95.1M** |
| 浏览器 speedtest 上传 | 4.4–13.0M（应用喂数限制，隧道窗口为空） |

### 7.13 单流大下载塌方与「下行窗口」（v0.11.4）

**现象**：22:45 后同窗对比——裸单流下载 1.13MB/s（线路本身变差），隧道单流只有 **0.77MB/s 且中途冻结 15s → 服务端 session 写超时 → RST 断流**；而线路好时（21:57）同样单流曾跑到 6.9MB/s。服务端日志 `write err after 15s (typ=2 len=16384)`，客户端日志显示 OPEN 后 19s 才有 open ack。

**定位（新增 `-pprof` 开关）**：下载进行中抓 goroutine dump：下载 session 的 reader 卡在 `frame.go:78`（一帧 payload 读到一半），`pumpDown` 等 rq（空），无任何锁竞争/通道堵塞 → **不是死锁，是网络级冻结**；服务端 socket 写 15s 不动 = 对端窗口关闭 15s。

**根因（自伤型 bufferbloat）**：fsrv/CDN 以 LAN 速度把 50MB 在 <1s 内灌给服务端，服务端经 loQ(16MB)+内核把整坨砸进 200ms RTT 的 WAN TCP → 队列爆满丢包 → CUBIC/RTO 退避冻结（1+2+4+8s≈15s 正好触发写超时）。裸 curl 不冻结，因为 fsrv 自身的拥塞控制从 slow-start 起就把 in-flight 压在 cwnd 内；隧道的 fsrv→服务端这一跳是 LAN，拥塞控制断链，WAN 段失去 pacing。

**修复（v0.11.4，仅服务端语义）**：
- **按流下行窗口 `downWindowBytes=1MB`**：`sStream.dlPending/dlWake`，pump 读到窗口满就停读后端；`session.writer()` 新增 `onData` 钩子，帧**真正写进 socket** 后回记信用（`closeStream` 时发 `dlWake` 解除 parked pump）。
- `writeTimeout` 15s→30s（低水位排空时写阻塞是合法的，不该秒杀 session）。
- `-pprof <addr>` 旗标（两端）：goroutine/heap 在线可抓，本次定位的关键工具。

**效果（同窗）**：修复前（23:05，线路差）：裸 1.13MB/s，隧道 0.77MB/s+冻结+断流。修复后（23:12）：隧道 dl1 **5.42MB/s**、dl2 **7.39MB/s** vs 裸 **7.0MB/s** —— **隧道单流下载追平裸 TCP**（50MB 无冻结、无 session 死亡）。这也解释了用户「下载 30–60M vs hy2 100M」的下行部分：重下载触发过同款塌方。修复后真实浏览器 speedtest（23:08）：**下载 94.63M / 上传 8.60M**（同时段线路上传池仅几 M，浏览器上传受应用流控+整形限制）。

### 7.15 上传 2–5M 徘徊：ETA「空闲饿死」bug + 窗口调优（v0.11.5）

**现象（用户，次日中午）**：下载已正常；上传 2–5M 徘徊。

**复现（13:45 白天）**：裸 x1 20.4 / **隧道 x1 12.6** / 隧道 x4 35.7 / 裸 x4 44.0 —— 隧道单流反而不如裸流。

**dbg 定位（决定性）**：8 条 lane 初始各分到 ~17 帧后，**除一条外全部冻结**（其余 lane sent 停在 ~20）。根因是 v0.11.1 的 ETA 降级规则：`400ms 无 ack 进展 ⇒ 判最慢`——但它同样命中**没有帧在飞、因此不可能有 ack 的空闲 lane** → 空闲→判慢→不派帧→更没 ack（自增强饿死环）。结果 8 lane 流塌成 ~1 lane，吞吐=裸单流。

**修复（v0.11.5，仅客户端）**：
1. **只对 `backlog>0`（有在飞帧未投递）的 lane 做 400ms 降级**；空闲 lane 保持按上次测速可用（`pickLaneSendLocked` 与 `resendFrame` 两处）。
2. **`streamWindowBytes` 2MB→6MB**：dbg 显示 inflight 顶死 2081292B；200ms RTT 下 12–14Mbps/流需要 ~2.5MB 在飞，x4 全员顶窗（tun 35.7 vs 裸 44）。6MB 仍远小于 `maxReorderBytes`，总量由 `globalWindowBytes=64MB` 兜底。

**效果（同窗对照）**：

| 场景 | 修复前(13:45) | 修复后(13:49/13:52) | 同窗裸线 |
|---|---|---|---|
| 隧道 x1（50MB 单流） | 12.6M | **21.0M** | 裸 x1 4.2–20.4M（大波动） |
| 隧道 x4 | 35.7M | **56.6M** | 裸 x4 44.0–46.7M |
| dbg lane 状态 | 8 lane 仅 1 条活跃 | 8 lane 全活跃、按 lane 速度配比（快 lane sent 520 vs 慢 lane 150） | — |

**浏览器上传再归因（13:54–57）**：4×8MB 上传流**均正常 spread**（35 次铺槽事件），每流实际交付 3.6–7.7MB/s；**浏览器上传进行中的同时刻，裸 x4 探测 p50=1.0M（max 7.3）**——本线 TCP 上传池是"突发桶"型（同一分钟内 0.5↔46M 摆动）。浏览器 Ookla 上传读数只是**当下池值 + 应用 ramp** 的反映；此刻 zhdata 交付（7.7M）已高于同时刻裸池。与 hy2 50M 的剩余差距 = **UDP 不受 TCP 整形**（路线 B 结论不变，见 §7.9）。

**部署**：仅客户端改动（服务端二进制不变、无需重启）；`dist/` 全平台重建；tag **v0.11.5**。

### 7.17 hy2 同刻满速对照暴露的两处下行/小流缺陷（v0.11.6）

**用户 A/B（15:20）**：hy2 **100M/50M 全程稳定**；紧接着 zhdata **5.9M/4.1M**。此前"线路池波动"解释不足以覆盖 hy2 同刻满速——继续查隧道自身。

**服务端排除项**：`tcp_congestion_control=bbr` 已在用（内核 5.14，tcp_bbr 已加载）——CC 差异不成立。

**发现 1：下行窗口 1MB「饿死 BBR」（下载塌方的第二个根因）**。15:24 同窗：裸 dl x1 **5.24MB/s** vs 隧道 dl x1 **1.38MB/s**。BBR 的 in-flight 目标是 带宽×RTT（40Mbps×200ms≈1MB+，探测相位还会翻倍再减半）；app 窗口 1MB 会把 socket 排空 → BBR 判定"应用受限"进入 ProbeRTT 塌缩。**v0.11.4 的 1MB 矫枉过正**（当时塌方主因是 16MB 火喉）。修复：`downWindowBytes` 1MB→**8MB**——只要不再制造 bufferbloat（16MB+ 才炸），BBR 自己会 pacing。复测（15:29，v0.11.6）：隧道 dl x1 **6.49 / 7.01MB/s（52–56M）**，同窗裸 dl 5.55MB/s（第二次裸只跑出 0.21MB/s——隧道比裸流更抗池波动）。

**发现 2：单 lane 小流的洞永远填不上（浏览体验杀手）**。15:0x 日志大量 `retransmit sid=... frames=3 lanes=1 total=0` 循环：小流只有 1 条 lane，重传候选排除原 lane → 无处重传 → 洞空转 12s 才被 watchdog 重置。修复：`checkStalls` 检测到洞且存活 lane<2 时调用 **`attachSpareLaneLocked`**（挑最空闲 session 临时加铺一条，重传走新 lane；服务端按 seq 去重）。复测：42 次 spare lane 挂载，**`total=0` 空转循环 0 次**，无其他异常。

**浏览器实测地面真值（15:32–15:35，v0.11.6）**：服务端下行 `backend pump done` 合计 **700MB/145s**（其中 speedtest 四流 39.8+43.2+44.5+57.3MB，下载段 ≈**59Mbps**）；客户端 `pumpUp done` 上传四流各 ~6.8MB/17–22s（上传段 ≈**10Mbps**，当时正处 TCP 池低谷——同窗裸测历史区间 1.0–46M）。

**与 hy2 的剩余差距定位**：隧道已能爆发 66M（zb x4 @15:24）且单流下载 ≥ 裸流；瓶颈是 **ISP 对本线 TCP 池的分钟级振荡（0.5↔46M）**，hy2 走 UDP 不受该整形。TCP 侧手段已用尽（BBR、多 lane、窗口、重传），**要稳定 50M 上传需路线 B（UDP/QUIC 承载）**——等待用户批准。

### 7.19 晚高峰「陈旧 session 桶衰减」与空闲会话换新（v0.11.7）

**现象（20:20 用户实测）**：下载 2.4M / 上传 12.7M。日志排查：上传失败大量是 `broken pipe`（Ookla 后端 8.3.86.3:8080 **主动掐断**慢速上传流，服务端随后对迟到帧回 `tReset unknown-stream`——隧道行为正确）；而下载塌方在 20:24 同窗复现：裸 dl **5.24MB/s** vs 隧道 dl **0.26MB/s**。

**A/B 定性（20:28，晚高峰）**：

| 实验 | 结果 |
|---|---|
| 隧道 dl（session 已存活数小时） | **0.067MB/s** |
| 同窗新开裸 TCP dl | 1.30MB/s |
| 重启客户端（32 条全新 session）立即 dl | **5.17MB/s** |
| 再测裸 dl | 6.17MB/s |

**根因**：ISP 对**长时间存活的 TCP 流**把桶衰减到 ~0.5M（下载方向尤甚）；新建流拿满额桶；hy2 的 UDP 不吃这一手。隧道下载走单一 owner session，正踩中衰减桶。之前上传靠 8-lane 多桶聚合不受影响，下载没有 spread，于是塌。

**修复（v0.11.7，仅客户端）**：`sessionRecycleLoop`——每 5s 扫描，把 **25s 无用户数据**（PING/PONG 不算）的最空闲 session 关闭重连（复用既有 1s backoff 重连路径）。池内 session 因此持续保持"新流"身份；活跃传输中的 session 不会被踢。新增 `cConn.lastAct`（atomic，dispatch/发送处刷新）。

**复测（21:5x 晚高峰，90s 空闲让池换新一遍后）**：隧道 dl **4.47 / 5.99MB/s（36–48M）**，同窗裸 dl 反而只有 1.01MB/s——隧道下载在晚高峰**反超裸 TCP**。真实浏览器 speedtest（21:36 晚高峰）：**下载 2.4M→80.8M**；上传读数 4M 但同窗 zb 探测裸 x4 p50 19.9 / 隧道 x4 p50 39.8——隧道上传 ≥ 裸池，Ookla 浏览器上传仍是应用喂数瓶颈（历史结论一致）。

**运维含义**：`-conns 32` 池的握手开销可忽略（48B 握手，每 5s 最多 1 条）；若 ISP 衰减更快可把 `sessionIdleRecycle` 调至 10–15s。观察发现：**持续有流量的流不衰减**（桶只随空闲衰减），因此回收只针对空闲 session，活跃传输永不被踢。

### 7.20 卡死 lane 的「4帧/400ms 排空」上传瓶颈（v0.11.8）

**背景**：以 v0.11.7 为基准专攻上传（用户指令：下载若因此不稳就回退）。用户两轮实测：下载 ~90M 正常，上传仅 2.4M。

**日志画像（20:48/20:55 两次 speedtest）**：4 条 ~8MB 上传流各耗时 **22–31s**（=0.26–0.36MB/s）；`pumpUp finish slow ... ackedSeq=443/511 waited=20s`——**一条 lane 完全停止投递**（sess 活着但 TCP 被整形到 ~0），其余 lane 早已送完。

**根因（数学实锤）**：服务端按序 deliveredPrefix 被卡 lane 的洞挡住；fast-hole 每 400ms 只重发 **4 帧** → 排空一条积压数百帧的卡 lane 需要 `N×0.4s`——**4 帧/400ms ≈ 0.4MB/s**，与观测 0.3MB/s 完全吻合。

**修复（v0.11.8，仅客户端）**：
- **卡 lane 整体迁移**：`checkStalls` 中 lane `backlog>0` 且 `600ms` 无投递进展 ⇒ 把该 lane 的**全部**待投递帧一次性 `resendFrame` 到最快 lane（每 lane 2s 限速防风暴；`laneMigT` 跟踪）。
- `holeResendBurst` 4→**16**。

**复测（21:09–21:10 晚高峰）**：Ookla 风格 zb x4×8MB：各流 **7.7–16s**（此前 22–31s），无 finish slow；**浏览器 speedtest：上传 2.4M→30.9M，下载保持 90.6M**。

### 7.21 回收风暴误伤活跃 session（v0.11.9）

**现象（21:15–21:35）**：用户报告下载又变 2M。日志 census（21:1x–3x 20 分钟）：**246 次 `slot lost: failing stream`**、105 session ended、98 recycle——回收把**仍挂有流**（浏览器 keep-alive、半空闲连接）的 session 也踢了，homed 流按 fail-fast 设计被 RST，且空闲池轮转风暴干扰新开测试连接。同时段线路本身进入深谷（裸 dl 0.57–1.13MB/s），两因叠加。

**修复（v0.11.9）**：回收对象收紧为 **`len(members)==0` 的完全空闲 session**——挂有任何流的 session 不回收（其零星流量本身也能延缓桶衰减）。上传侧 v0.11.8 改动（卡 lane 迁移/burst16）只作用于上行 sentq，对下载路径无影响，经对比保留。

**验证（21:36–21:47）**：守卫上线后 `slot lost: failing stream` **0 次**（此前 246/20min）；recycle 与 session ended 严格 1:1（只重连空 session）。同窗下载配对：隧道 **2.26MB/s vs 裸 0.57**、**3.95MB/s vs 裸 1.62**——深谷期隧道下载仍 **2–4 倍于裸 TCP**。用户 21:15–21:32 的"2M"= 线路 TCP 池深谷（同窗裸下载也只有 0.4–1.1MB/s）+ 回收风暴叠加，两个因素均已定位；hy2 走 UDP 不受该整形，差距属路线 B 范畴。

### 7.22 卡 lane 迁移限「大流」——修复 download test error（v0.11.11）

**过程**：用户要求回退到 v0.11.7 复测（下载 45M/65M 正常）→ 以 v0.11.7 为基准仅重做上传路径（v0.11.10）→ 下载骤降并出现 **download test error**。

**日志对比（按分钟归一）**：v0.11.10 的 `finish slow` 是 v0.11.7 基准的 **9 倍**（5.5/min vs 1/min）；服务端 `tReset unknown-stream` **227 次**。机制：迁移条件（600ms 无 ack）对 **1–2 帧的小流**（GET 请求帧、tClose 尾帧）也触发，把帧重投到**服务端已关闭**的流上 → tReset 风暴 → 部分打到活跃下载流 → 浏览器 RST（download test error）。

**修复（v0.11.11）**：迁移只对 **bulk 流**生效（`len(sentq) ≥ 64` 帧 ≈ 1MB；speedtest 上传流积压数百帧达标，小流完全走 v0.11.7 原路径）；`holeResendBurst` 16→8。

**复测（22:15）**：浏览器 **下载 111.9M**；churn 回到基准水平（finish slow ~1.5/min、tReset 9 次/2min）；上传 7MB 流 15.7–20.9s（基准 22–31s）。

### 7.23 上传/下载 session 池分离（v0.11.13）

**双实例对比设施**：v0.11.7 原样常驻 **127.0.0.1:49880**（slot 32–63，靠 `-slotbase` 纯寻址参数，worktree `zt0117/`）；新版常驻 49888（slot 0–31）。用户可随时换代理端口对比。

**用户复测（22:5x）**：即使迁移已默认关闭（v0.11.12），49888 下载仍差于 49880（r1 NEW 0.84 vs OLD 0.28；r2 6.9 vs 7.7；r3 8.3 vs 0.23 MB/s，交替顺序）。结论：干扰不止迁移——**共享 session 上任何上传活动（spread/hole/重传）都会排在下载流的 TCP ACK 前面**，且带浏览负载的 49888 池其 session 长期不死（桶衰减）。

**结构修复（v0.11.13，仅客户端）**：`-dlconns N`（建议 =conns/2）把 session 池分成 **下载池**（后 N 条：只做 home/owner，承载下行+控制/ACK）与**上传池**（其余：只做 spread/ Spare/重传 lane）。改动点：home 选择、spread 候选、备用 lane 候选、lane 打分四处加池过滤（`split`+`dlStart`；手工构造的 clientApp 零值默认不分裂，单测不受影响）。小流的 1–2 帧请求仍走 home（开销可忽略）。

**验证（23:0x 深夜池）**：全量测试 ok；dl 交替 3 轮 NEW 3.4/0.6/1.4 vs OLD 7.0/3.1/2.2 MB/s（晚段池振荡内 NEW 未再出现此前 0.1–0.5 的系统性塌方）；上传 zb x2 正常；浏览器 dl 7.6/up 7.3（深夜线路深谷）。

### 7.24 上传专项：池上运行迁移 + 尾块重传（v0.11.14/v0.11.15）

池分离后 `-migrate 1` 重开（迁移只作用于上传池，下载免疫），专修上传两处：

- **v0.11.14 迁移门槛按「流累计发送≥64帧」判定**（原来按当前积压≥64）：大流**尾部**（队列只剩 1–63 帧）不再被豁免——修 `finish slow sid=1 ackedSeq=1651/1671 waited=20s` 的尾块病。GET 小流累计才 1–3 帧，仍被排除（不触发 unknown-stream tReset 风暴）。
- **v0.11.15 尾块 hole 重传豁免「后方有帧」抑制**（`finSent` 标志）：流的最后几帧后方无帧，旧规则（`len(sentq)>1`）不对尾块快速重传，只能等迁移的 600ms+2s 闸门；上传池整体安静时（speedtest 间隙）连迁移都停摆——实测 `sid=7 ackedSeq=20/394 waited=20s`（**94% 尾部卡死**）。现尾块按 400ms timer 无条件重发；流中部孤帧保持旧抑制防重复洪水。

**上传基准（23:3x 深夜，同窗裸流对照）**：

| 场景 | 隧道 | 裸 TCP |
|---|---|---|
| x1 30MB | 14.7M | 5.2M |
| x1 20MB | 17.3M | （池振荡） |
| x4 8MB（Ookla 风格） | 流完成 1.4–16s（**20s 卡死 0 次**；v0.11.7 基准 22–31s） | — |

### 7.25 上传收尾与慢 lane（v0.11.16/v0.11.17）

**用户现象（23:4x speedtest）**：开始 1 秒 ~100M（窗口/内核缓冲吸收，日志 max 采样 233M）→ 迅速 <1M → 徘徊 2M。逐流证实：4 流都正常 spread 到 8 lane、发完 8.4MB（21s），**收尾卡**（`finish slow ackedSeq=540/682`），服务端 `hole unfilled >12s -> reset` + Ookla 后端 `broken pipe` 把流掐掉。同时刻**裸 x4 同形**（max 88.6 → p50 18 → p10 6.8）：回落主形是 ISP 对 TCP 流的秒级衰减，非协议引入。

- **v0.11.16**：① stall sweep 也纳入「数据已全 ack 但 fin 未处理」的流（`inflightBytes==0` 曾被跳过 → fin 卡死 20s → 服务端 reset 掐流）；② **tClose 每 ~1.5s 重发**直到处理（`finSeqVal/finT`；服务端按 seq 去重）；③ **迁移判据扩展至「慢 lane」**：lane 持续 trickle ack（laneT 不过期）但按当前速率 2s 内排不完积压（`laneRate*2 < backlog`）也整体迁移——深夜深谷 `ackedSeq=89/389` 卡 20s 即此类。
- **v0.11.17**：**上传池 session 空闲 10s 即换新**（下载池保持 25s）：speedtest 间隔（10–25s）里旧上传池桶已衰减而裸测流总是新连接（深谷裸 x4 13.1M vs 隧道 2.1M）。换新后 8MB 流最快 4–5s。

**深夜 23:5x 池深谷复核**：隧道 x4 p50 6.3 vs 裸 6.8（追平）；另有 p50 2.1 的窗口恰为裸流也被腰斩的分钟（max 12.6）。结论：曲线形态由 ISP 秒级衰减主导；协议侧已把「比裸流更差」的三处收尾病（fin 卡死/慢 lane/陈旧桶）全部修掉。

### 7.26 调优固化 + tReset 止损 + 双实例槽位寻址（v0.11.18 / v0.11.19 / v0.11.20）

- **v0.11.18**：把此前靠命令行调出来的组合固化成默认——`-dlconns` 默认 **-1（auto=conns/2）**、`-migrate` 默认 **1**。起因：用户 22:5x 用默认参数双轮下载拿到历史最佳 136M / 70M，且曾被客户端被重启回落旧参数坑过，故将调优写入默认，避免"没带 flag"就退化。

### 7.27 zhv5 大体积上传分桶（v0.12.0）

**动机**：遗留上传虽已 spread+迁移，但**整条流共享一个「已投递前缀 deliveredPrefix」**——任一 lane 上出现空洞超过 12s，服务端 hole watchdog 就把**整条流** reset。speedtest/Ookla 的多请求上传正是被这一下整流掐死（`hole unfilled sid=… -> reset`，随后 `broken pipe`）。scp/pscp 之所以稳，是因为它是单条恒定流跑在池均值上；speedtest 是"多请求、请求间长静默"的形态，撞上整流死亡。

**用户设计（采纳）**：设最小桶大小 + 最大桶数两参数，把正文按此切分，**每个桶独立传输**；某桶 block/timeout/reset 只重置该桶，已完成桶释放的容量把剩余未传区间重新填进空桶，直到全部上传完成。

**实现（zhv5）**：
- 客户端 `pumpUp` 先缓冲请求头到 `\r\n\r\n`，解析 method+Content-Length；命中 **POST/PUT/PATCH 且 2·bucketMin(512KB) ≤ CL ≤ 512MB** 才分桶，否则完全走遗留路径。
- **leader 流只带请求头**（保留后端连接、下行通道、字节序）。正文 `[0,CL)` 切成 `K=clamp(ceil(CL/512KB),1,16)` 桶、每桶 `B=ceil(CL/K)`。
- 每桶 = **独立成员流**（独立 sid、独立窗口、独立服务端 hole watchdog），走上传池 lane；成员 tOpen payload 用 `0xFE|leaderSID(2)|off(8)|len(8)|final(1)`（`tOpenBucketMember`，区别于 `atyp|addr|port`）。
- **成员并发上限** `maxActive=2×上传lane数`（并排队），避免 16 桶同时挤爆全局 64MB 窗口导致重试桶拿不到 credit（acked=0）。
- 桶失败：先原区间重试一次，再**二分**成两个更小的桶重试（有界次数），彻底失败才放弃整条上传。`pickUpConnLocked` 重试时优先选**已连接**的 lane（跳过正在重连的）。
- 服务端：成员 tOpen → 按 `leaderSID` 找 leader，惰性建 `upGroup{doneOff,pending[off]}`；成员正文有序字节进 `st.rangeBuf`，成员 fin 时交 `grpDeliver` 按 off 推进、**连续区间**写 leader.upq（后端按字节序收到 header+全部桶）。leader 在桶组开启期间把 header 之后的上传 chunk 暂存 `holdBuf`，桶组完成再冲刷；`CloseWrite` 仅在**流级 fin 且桶组完成**时发。慢后端按遗留契约背压（`streamStallTO` 才 reset 该流，绝不静默丢区间）。
- 服务端 magic 校验同时接受 `zhv4` 与 `zhv5`：**部署顺序=先升服务端、再升客户端**，旧的 zhv4 基线实例（如 49880）无缝继续。

**实测（2026-11-18 上午，C498）**：
- 单流 20MB PUT：`bucket up cl=20971520 ranges=16` → 服务端 `bucket group done body=20971520`，**字节精确**；期间个别区间随 session 回收重挂（sid 17/18/19 重挂），group 仍补齐——即用户要的"桶级独立、坏了补该桶"在真实链路生效。
- 4×25MB 并发 PUT（含 probe 小流）：64 成员桶聚合送达，无整流死亡；受 ISP 上行池 ceiling 限制（本窗口约 17–20M）。
- 下载 A/B（curl 单流经隧道 vs 49880 zhv4 基线）：zhv5 2.17/1.04/1.26 MB/s ≈ 基线 1.25/9.0/1.76 MB/s（单流受 ISP 逐流整形，宽方差），**无回归**。
- 客户端全套 `go test`（含新增 `TestBucketUploadE2E`、`TestBucketUploadSingleLaneSlow`）连跑 3 轮全绿；`TestRetransmitSurvivesSessionKill` 显式压回遗留路径（CL<1MB）以继续守护遗留 retransmit 不变量。

**加固（同版内）**：初版重试阶梯只有 3 次，重负载（4×25MB 并发 + probe）下 session 回收抖动会让部分区间连续被 reset 而耗尽重试 → `bucket range dead -> upload fails`（单流 20MB 稳定，多流偶发数条判死）。把阶梯扩到 **8 轮 + retries==2/4/6 各二分一次**，仅当区间缩到小于半桶（<256KB）且耗尽重试才判死该上传。改后同参数 4×25MB 重负载 **`range dead` 归零**，四条流全部 put done。

## 9. 威胁模型声明

- 防：协议签名识别、被动 DPI 分类、一般主动探测（无限频时端口只表现为"未知 TCP"）、按 UUID 的设备/连接数管控。
- 不防：拿到客户端二进制者离线解密该用户流量（key=UUID，无前向保密）；流量统计（体积/时序/单连接长寿命）相关性分析。
- 若单个用户二进制泄露，不影响其他用户（key 按 UUID 隔离）。轮换 UUID 即换 key。

### 10.5 关键参数现状（v0.11.4）

`maxSlots=64(协议) / -conns 32(生产)`；**`spread=8`（逐流铺槽启用，自动预算 `min(spread, conns/活跃大流数)`，全局 lane 上限 = conns）**；上传窗口 **按投递**：`streamWindowBytes=6MB/流`（v0.11.5；2MB 在 200ms RTT 下顶窗限吞吐）、`globalWindowBytes=64MB`、`holeResendTO=400ms`（fast-hole 重传，**16 帧/次**，v0.11.8 从 4）、**卡 lane 整体迁移（v0.11.8：lane `backlog>0` 且 600ms 无投递进展 ⇒ 全部待投帧一次性重投最快 lane，每 lane 2s 限速，`laneMigT`）**、`holeTimeout=12s`（服务端未填洞重置；**仅 backend 就绪后才计洞**）、`laneRateInit=50`/`laneRateMin=0.5`（ETA 分配）；**ETA 计分 = `(laneSent-laneAck + 1)/laneRate`**（真实 TCP 排队，不用"未释放窗口字节"）；**400ms 无进展降级仅对 `backlog>0` 的 lane 生效（v0.11.5：空闲 lane 不降级——否则"没帧→没 ack→判慢→没帧"饿死环把 8-lane 流塌成 1 lane）**；**下行窗口 `downWindowBytes=1MB/流`（v0.11.4：pump 停读后端直到 writer 把帧交进 socket 回记信用，防 LAN 火喉灌爆 WAN）**；`writeTimeout=30s`（v0.11.4 从 15s）；`ackEvery=8` 或投递进展且距上次 ack≥10ms 即回 tAck，载荷 **count|deliveredPrefix**；`maxReorderBytes=16MB`（窗口 2MB 后只作安全网）；服务端越窗/hole 超时**只重置该流、不阻塞 reader**；`-train` 默认 0；DNS 三级容错+缓存；**`-pprof 127.0.0.1:6060`（两端）在线抓 goroutine/heap**；客户端 `ZHD_DEBUG2=1` 输出每流 inflight/ackedSeq/lane pend/ack/sent/rate 诊断；`dispatch slow`/`pumpDown slow` 日志（>500ms/>2s）定位冻结；**`sessionIdleRecycle=25s` + 5s 扫描（v0.11.7：空闲 session 自动换新，PING/PONG 不续命，防 ISP 对陈旧 TCP 流的桶衰减；v0.11.9 收紧：只回收 `members==0` 的完全空闲 session，防回收风暴 RST 活流）**。**协议 magic `zhv4`：客户端与服务端必须同版本**。

**浏览器 smoke test 判读**：`tools/run_speedtest_retry.ps1` 的 leaf 布局 = `[share id, 下载Mbps, 上传Mbps, ping/jitter/loss...]`（曾把 id 当下载误读）。服务端 `tools/ookla_par.sh <host:8080> N SIZE` 可测 C498→Ookla 后端腿容量（实测 4-8 并发 240-260Mbps，后端不是瓶颈）。

#### 10.6.1 路线 A 实现记录（v0.11/v0.11.1，已落地）

与最初草案的差异（重要）：
- **没有**用「按 lane ack 计数推算 seq」（重传产生的重复帧会让 lane 计数与客户端发送列表错位），改为 **服务端在 tAck 第二字直接回报 `deliveredPrefix=rx.next-1`**，客户端按 seq 前缀释放；lane count 只用于速率测量。
- 重传缓冲用 `[]*sentFrame`（seq 递增队列），窗口按字节（2MB/流）；**fast-hole 重传**只重发最前面的洞帧（400ms/4 帧），而不是按 lane 迁移整窗帧——按 lane 迁移曾造成"窗口全部堆到一条慢 lane + 洞在 lane 间移动"的活锁。
- **ETA 分配**替代轮询：`(backlog+1)/laneRate` 最小者优先，**backlog=`laneSent-laneAck`（真实 TCP 排队帧）**——用"未释放窗口字节"会在有洞时把健康 lane 一起抬高、反而喂给慢 lane；laneRate 为 tAck 计数增量 EWMA；400ms 无进展判为最慢。否则轮询下吞吐 = N×最慢 lane（§7.11）。
- 停摆检测改为 **app 级 200ms sweep**（避免每流一个 ticker goroutine）；服务端 hole watchdog 12s；服务端去掉 detach 时的立即 gap truncate。
- **v0.11.3 教训（阻塞点审计）**：任何在 `app.mu` 内或 session reader 路径上的通道发送都必须非阻塞/有界——`tClose` 的无界 rq 投递和 `ctrlQ` 满时的阻塞 `sendCtrl`（经 `openStreamLocked` 在锁内）各冻结过一次全部 session。
